| # | Decision |

| J1 | `AddParameter` request: `unit_path`, `tag`, `name_en`, `description_en`, `type` (TypeExpr, J3), `s7_address`, `value`, `limits[i].leaf_path/min/max/max_length`. `value` is required. `limits[]` may be empty. `UpdateParameterDefinition` request: the same definition fields; when `type` changes, `value` and `limits[]` are required, otherwise they are absent and unchanged. | J2 | A parameter is outdated when any `plc_type` in its resolved type tree (the type itself, every member, every element type, at any depth) has a successor revision. The rule lives in domain-model 2.2 and ADR-0018 with the same sentence |
| J3 | Type expressions. `TypeExpr` grammar (value object in domain-model 2.1): `<primitive>` (`INT`), `STRING(<n>)`, `WSTRING(<n>)`, `<udt_name>@<revision>` (`ST_Zone@3`), `ARRAY[<lo>..<hi>(,<lo>..<hi>){0,2}] OF <TypeExpr>`. `AddParameter`, `UpdateParameterDefinition` and the `members[i].type` field of `DefineUdt` carry a TypeExpr string. `EnsureDerivedType` resolves it: primitives and UDTs by lookup, `STRING(n)`, `WSTRING(n)` and arrays by get-or-create. Error `E-PLT-013 DerivedTypeInvalid` covers a parse error, an unknown UDT or revision, a type not on the platform, and more than 3 dimensions. Remove the sentence "array types have no route" |
| J4 | `recipe-app` defines `StorageError` (variants: `Duplicate { constraint }`, `MissingReference { constraint }`, `Constraint { code, message }`, `Deadlock`, `StatementTimeout`, `PoolTimeout`, `Other`). `AppError::Storage(#[from] StorageError)`. `recipe-db` has no public error type: it maps `sqlx::Error` into `StorageError`. Registry rows E-DB-001..008 change owner to `StorageError::*` (crate recipe-app). overview 5 crate table: recipe-db "error type: none public, maps into `StorageError`" |
| J5 | reliability 4.2 rule: a path value that is a domain value object with its own error code returns that code with 422 (LangCode → E-RCP-027, UnitPath → E-PLT-002/003, S7 address never in a path). A path value that names a resource returns 404 `E-WEB-005` when it does not exist |
| J6 | `0003_grants.sql` order: (1) every GRANT and REVOKE on the audit objects runs first, while `recipe_migrator` still owns them; (2) `SET ROLE audit_owner` is not used; (3) then `ALTER … OWNER TO audit_owner` (the grantor becomes the new owner); (4) no sequence grants (identity columns need none for INSERT); (5) no `REVOKE ALL … FROM recipe_migrator` after the transfer (the old owner's implicit privileges move with the ownership). CI test: apply 0001–0004 as `recipe_migrator` on a fresh cluster, then run the grants test |
