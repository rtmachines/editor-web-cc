# Security review (design stage) — 2026-10-12

Reviewer: independent security-auditor agent (Opus), read-only. Sources: general-draft.txt, api.md, data-model.md, reliability.md, domain-model.md (2.3, 2.4, 3, 4, 5), overview.md (2, 3, 6, 9), ADR-0002, 0003, 0004, 0005, 0013.

## CRITICAL

**C1. The export document has no integrity seal, and approved content is never checked at export time**
Where: adr/0002 Decision; api.md §6.1 and §6.3; data-model.md §6 (ApproveVersion and ExportVersion rows). ASVS V8, IEC 62443-3-3 SR 3.1.
Scenario: The JSON file leaves the system on a USB stick or a shared folder. Nothing lets the transfer system detect that a setpoint or limit was edited after download. Export also serializes whatever the database holds at that moment, so a row changed after approval (see H1 and H7) goes out with the original approver's login on it.
Fix:
- At ApproveVersion, compute SHA-256 over an RFC 8785 (JCS) canonical form of the payload, without exported_at and exported_by.
- Store the hash in an immutable `recipe_version.content_sha256` column and in the after_state of the RecipeVersionApproved audit entry.
- At export: rebuild the payload, re-run the I7 validation, compare the hash, and refuse with an E-EXP error on mismatch.
- Sign the document with Ed25519 (detached JWS or a `signature` field). Keep the key in a Docker secret, never in the database.
- Make these contract duties of the transfer system: verify the signature, require status == Approved, and compare the hash with `/approved` before loading.
- Put content_sha256 and signature into schema v1 now. Adding them later is a breaking v2 change.

## HIGH

**H1. The database does not enforce the version state machine or freeze the identifiers that appear in exports**
Where: data-model.md §4 (no transition trigger) and §5 (recipe_app has UPDATE on recipe_version, machine, unit, recipe); domain-model.md §3 I4 and §4; reliability.md §1.2.
Scenario: Using only its own grants, recipe_app can set an Approved version back to draft, edit its parameters (trigger 4.1 then passes), and set it back to approved with any approved_by. It can also UPDATE unit.path, machine.code or recipe.reference_number, which silently changes the unit_path or machine of an export that api.md §6.3 calls immutable.
Fix: BEFORE UPDATE trigger on recipe_version that allows only draft→approved, approved→retired, and setting deleted_at on a draft; freeze number, recipe_id, based_on_version_id, created_by, approved_by, approved_at, content_sha256 once set; freeze triggers on machine.code, unit.path/parent_id/machine_id, recipe.reference_number/machine_id while any non-draft version references the row; one integration test per forbidden transition, run as recipe_app.

**H2. One person can change limits, change values and approve, with no re-authentication at approval**
Where: adr/0013 (Option C rejected); api.md §3.3; overview.md A5. ASVS V3.7.1.
Scenario: A careless engineer, or anyone at an unlocked HMI workstation with an engineer session (12 h absolute timeout), can widen a process limit, move the value inside it and approve within a minute. No second person ever sees the change.
Fix: default `approval.separation_of_duties = true` (approver must not be the creator or any editor of the draft; record editors; enforce in ApproveVersion and in the H1 trigger; plant can turn it off only through an audited config value); password re-entry on approve stored as e-signature in the audit entry; approve page shows a diff against the current Approved version with limit changes highlighted; widening a limit needs an Administrator.

**H3. Login throttle: any account can be locked out permanently, the limit has a race, and spraying is not covered**
Where: api.md §7.4; data-model.md §3.6a and §6 (Login row); adr/0004; overview.md A22.
Scenario: Every role can see logins (export approved_by, history page). Any host on the plant network can send 5 wrong passwords per account every 15 minutes and keep every operator and administrator out indefinitely, because the 429 is returned before the password check and there is no unlock use case. The count runs before the insert under READ COMMITTED with a ~250 ms hash in between, so parallel requests all read 4 failures. The per-login key does nothing against one password tried on every account.
Fix: exponential back-off keyed on (normalized login, client IP) plus a per-IP failure budget and a global failure-rate alert; insert the attempt row first or take `pg_advisory_xact_lock(hashtext(login))` and count in the same transaction; exempt a (login, workstation) pair with a recent successful login (device cookie); audited Administrator `UnlockLogin` use case; count failed ChangeOwnPassword checks in the same table.

**H4. Unbounded Argon2id work lets one unauthenticated client OOM-kill the app**
Where: reliability.md §2.2, §7.4, §7.8; api.md §7.4.
Scenario: Each POST /login with a new random login runs a full Argon2id hash in tokio's blocking pool (up to 512 threads). About 25–30 concurrent requests at OWASP memory cost exceed 512 MiB; the kernel kills `app`.
Fix: one global semaphore around every Argon2 call (permits = memory budget / m_cost, e.g. 4; acquire timeout 2 s, then 503 with Retry-After); per-IP request limit before any hashing; permits × m_cost ≤ 25 % of the container limit; login flood in the soak test.

**H5. Migrator credentials sit in the runtime container, and the schema owner also owns audit_log**
Where: adr/0003 ("app runs migrations at start"); data-model.md §8; contradicts reliability.md §5. data-model.md §5 makes recipe_migrator the owner of all objects.
Fix: make reliability §5 the rule, correct ADR-0003 and data-model §8, mount the migrator secret only into `migrate`; a NOLOGIN `audit_owner` role owns audit_log; revoke TRUNCATE and all rights on it from recipe_migrator; at startup the app refuses to serve if current_user is a superuser, owns any table, or has privileges beyond the expected grant list.

**H6. The audit log has no tamper evidence and no copy outside the database**
Where: adr/0005; data-model.md §3.12; reliability.md §3.6 and §7.7.
Fix: hash chain (BEFORE INSERT trigger, SECURITY DEFINER owned by audit_owner, `SET search_path = pg_catalog`, serialized by an advisory lock, sets prev_hash and entry_hash); ship new entries and the chain head every few minutes to an off-host append-only sink; nightly verification job.

**H7. Backups expose live sessions and password hashes, and are restored without an integrity check**
Where: reliability.md §7.7 and §7.10 step 7; adr/0004; data-model.md §3.6.
Fix: store SHA-256(session id) in session.id; `pg_dump --exclude-table-data=session --exclude-table-data=login_attempt`; dedicated recipe_backup role with pg_read_all_data; encrypt each dump with `age` to an offline key; signed SHA-256 manifest verified before every restore; restore runbook truncates sessions and re-applies deactivations from the off-host audit copy.

## MEDIUM

**M1. Session fixation and login CSRF are not addressed** — call `Session::cycle_id()` and issue a new CSRF token on login, logout, password change and role change; pre-session CSRF token (signed double-submit cookie) for /login and /lang; require Origin or `Sec-Fetch-Site: same-origin` on every POST; /lang redirects only to a validated same-origin relative path.

**M2. Cookie and transport specs contradict each other, nothing fails safe behind the proxy** — one normative spec: `__Host-recipe_session`, Secure, HttpOnly, SameSite=Strict, Path=/, no Domain; tower-sessions ids are 128 bits; refuse to start with secure=false outside a dev build; `app` uses `expose`, never `ports`; Caddy mandatory (re-encrypts to upstream if plant terminates TLS elsewhere); HSTS ≥ 1 year; trusted-proxy CIDR list for X-Forwarded-*.

**M3. No CSP and no htmx hardening: stored XSS path from ProcessEngineer to Administrator** — CSP `default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`; move the row_version script to a static file; htmx config allowEval=false, allowScriptTags=false, selfRequestsOnly=true; `hx-history="false"` on body; never put user data into hx-* attributes; ban `|safe` in review; nosniff, `Referrer-Policy: same-origin`, `Cache-Control: no-store` on authenticated pages; XSS payload corpus in HTTP tests.

**M4. A role change does not end sessions, and the role is never reloaded per request** — build CurrentUser from session → app_user on every request (role, is_active), or bump `app_user.auth_epoch` on role change/reset/deactivation and compare per request; SetUserRole deletes target sessions in the same transaction; cover in the permission-matrix test.

**M5. Bootstrap admin password and administrator password reset** — replace the migration with `recipe-server create-admin` (password from stdin or secret file, no-op when an active admin exists); `app_user.must_change_password` set on bootstrap and admin reset, session can only reach /me/password until cleared; reset generates a one-time password shown once; check new passwords against a breached list.

**M6. Placement of secrets and privileged PostgreSQL credentials** — Docker secrets (`*_FILE`) only; superuser password exists only in `db`; dumps use recipe_backup; measure free disk with statvfs on a read-only mount inside `app`; do not publish port 5432.

**M7. Export has no machine identity, and Operators can export Retired versions** — per-system API tokens (hashed, scoped to VersionExport and listed machines, expiring, revocable, audited) accepted only on /export/* and never with cookies there; only /approved returns a loadable document; Retired export limited to Administrator and ProcessEngineer, carries `"loadable": false` in the signed body and a RETIRED_ file-name prefix; resolve the contradiction between the documents.

**M8. Audit and event logs do not record the source; failed-login records leak data and grow forever** — add client_ip (via trusted proxy), truncated user_agent and session_ref to audit_log and the http span; store the login in LoginFailed only when it matches an account, otherwise HMAC(login); alert on failed-login rate, CSRF failures, Forbidden for UserManage; extend redaction to X-CSRF-Token, csrf_token, DATABASE_URL, bootstrap variables, Debug of config structs.

**M9. Health endpoints: documents disagree on exposure, and /readyz is an unauthenticated database probe** — serve health on a separate internal listener that Caddy does not route; on the public site `respond /healthz* /readyz* 404`; cache the readyz result for 5 s; public body says only ok or not ready.

## LOW

**L1. Account-state oracle** — same 401 body and same hash work for inactive, unknown and wrong-password cases; log the real reason only.
**L2. Read-only mode contradicts audited export and login** — define read-only as "commands blocked; session, login_attempt and audit inserts allowed", reserve disk margin; if the audit insert fails, the export fails.
**L3. ProcessEngineer delete rule differs between documents** (adr/0013 vs api.md §3.3) — pick one rule, implement once in DeleteRecipe, test both conditions.

## Verdict
1. Not ready to implement as written: 1 CRITICAL and 7 HIGH. Nothing anchors integrity along the path from approval to the PLC (database state machine, export seal, audit chain, backups), and the unauthenticated login path can lock out or crash a 24/7 system.
2. Every fix is a design change and is cheapest now: C1 has to go into export schema v1, and H1, H5 and H6 into migration 0001.
3. Reconcile the contradictory documents first (SameSite, where migrations run, health routing, Retired export, seed admin, the ProcessEngineer delete rule).
