## 2. Changes

The plan uses three OpenSpec changes. Each change gets its own branch and its own pull request. Each change follows the cycle of `CLAUDE.md` "Workflow".

| Change | Scope | Implementer | Depends on |
|---|---|---|---|
| A `review-code-fixes` | Code and tests with no design decision | Sonnet, Haiku for `[mechanical]` tasks | None |
| B `review-design-fixes` | ADRs, `docs/architecture/`, and the code that follows them | Sonnet for code, Haiku for simple doc edits | Change A for F-12, because both touch `recipe-domain` errors |
| C `review-deploy-fixes` | `deploy/`, `.github/`, and the CI scripts | Codex `gpt-6.1-sol` | None |

- Opus writes each proposal and each design, and reviews each change.
- Changes A and C touch different files. They can run in parallel.
- Change B starts after change A is merged.

## 4. Order of the work

1. Write the proposals of change A and change C with `openspec-propose`. The owner approves each `tasks.md`.
2. Run changes A and C in parallel. Each task gets one agent.
3. Review each change with `code-review` (Opus) and Codex `gpt-6-astra` at the effort `high`. Merge each pull request.
4. Write the proposal of change B. The owner approves its `tasks.md`.
5. Run change B, review it, and merge it.
6. Write a closure record `2026-11-13-fix-plan-closure.md` in `docs/plan/review/`.
