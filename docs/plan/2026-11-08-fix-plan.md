## 4. WP1: change `backup-result-alerts`

### 4.1 D7-1: an alert for a failed restore test or base backup (MEDIUM)

- ADR-0151 (new, amends ADR-0067 and ADR-0068): each scheduled check writes a result file, and the job `alerts` reads it (decision Q-G (1)).
- Design points for the propose step:
  - `restore-test` writes its result to `/backups`. `basebackup-once` writes its result to `/wal`. The service `app` already mounts both volumes read-only (`deploy/compose.yaml:160-161`).
  - The file name must not match the set grammar of `reliability.md` §7.7. Then the retention and the `BackupDirectory` scan ignore it.
  - The script writes the file through a temp name and a rename, so a reader never sees half a file.
  - The file holds the time and the result: `passed` or `failed`. It holds no path of the host and no secret.
  - Two new conditions follow `backup_age`, for example `restore_test` and `base_backup`. A condition fires on a result `failed`. It also fires when no result exists or when the newest result is older than a limit.
  - The limits are new rows of `reliability.md` §7.11. A weekly job needs a limit above 7 days, for example 8 days.
  - Each new fault code gets its row in `reliability.md` §1.2 before its variant.
- Documents: `reliability.md` §3.7 (two rows), §7.7, and §7.11. The runbook gets the steps for each new alert.
- Spec delta (`operations`): one requirement with three scenarios: a passed result, a failed result, and a missing or old result.
- Tasks:
  1. Failing test (Codex, `deploy/pgtools/tests/`): `restore-test` writes the file with `failed` after a failed restore and with `passed` after a passed one.
  2. Failing test (Codex, `deploy/pgtools/tests/`): the same test for `basebackup-once` and a failed `pg_verifybackup`.
  3. Fix (Codex, `deploy/pgtools/`): both scripts write the result file.
  4. Failing test (Sonnet, `recipe-app`): the job `alerts` sends each new condition and keeps the order of `AlertCondition::ALL`.
  5. Fix (Sonnet, `recipe-app`): the two variants of `AlertCondition` and the port that reads a result.
  6. Failing test and fix (Sonnet, `recipe-server`): the adapter reads the file under the time limit of ADR-0133. A malformed file gives a fault, not a passed result.
  7. Docs (Haiku): `reliability.md` §3.7, §7.7, §7.11, §1.2, and the runbook.
- Risk: an existing installation has no result file until the first Sunday run. The ADR decides whether the first run after the upgrade starts the clock.
